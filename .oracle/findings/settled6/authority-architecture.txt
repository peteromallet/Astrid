1. **P0 — installed admission does not bind executable Python bytes.**  
   §§III.2, III.5–7 bind an installed record to normalized manifest/provenance digests and verify only the captured manifest plus consumed resource handles. §IV.4 explicitly excludes Python from the resource grammar. Therefore, mutating an installed revision’s `.py` after snapshot capture is undetected; a lazy import can execute code that was never covered by the accepted v2 record. WP1/WP6 test manifest/resource mutation, but not Python-module mutation or an explicit immutable-revision invariant. This leaves strict v2 admission authoritative for metadata, not executable content. Resolve as an investigation: prove published revision roots are immutable, or define a narrow Python module origin/digest guarantee.

2. **P1 — migration table ownership can diverge from authoritative SQL.**  
   §II.3 makes `database.migrations[].tables` the ownership projection and says “the migration first creating a table records ownership.” §§VI.2–4 require collision checks and preserve SQL bytes, but specify no executable check that each declared table is actually created by that migration, that no SQL-created table is omitted, or that later `ALTER` claims do not invent ownership. Existing evidence shows collision registration operates on declared descriptors (`astrid/core/schema_packs/registry.py:162-180,221-294`), while migration safety checks bytes/state rather than SQL schema semantics (`migrations/runner.py:233-322`). A malformed or drifted declaration can bypass canonical table ownership while SQL remains checksum-valid.

3. **P1 — backup creation remains underspecified as a catalog consumer.**  
   E4 identifies backup creation as a raw `schema_migrations` reader without a registry (`astrid/core/backup/operations.py:1122-1172`), with restore separately rebuilding composition (`:1253-1296`). WP4 says to thread a snapshot and permits “raw database reads” after a shared probe, but does not state that backup and restore must use the same catalog-derived database projection, nor require operation receipts binding expected composition. The generic WP6 “backup/restore” check cannot prove criterion 7 without that scenario.

**North Star disposition: not yet aligned.** These are new closure gaps, not the superseded Wave 1–5 objections: executable code integrity, SQL/ownership agreement, and a fully specified operational backup/restore authority path remain unresolved.
