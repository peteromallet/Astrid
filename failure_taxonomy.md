# Failure Taxonomy — eval-mh-59 + eval-threaded-59 (14 failed scenarios)

## Executive summary

All 14 failures are **harness/infrastructure failures, not graded model failures** — none of the 14 produced a gradable product, so zero of them measure the model's workflow-diagnosis ability. The 14 split into four classes: (A) provider/account transients — timeouts, provider unavailability, OpenRouter credit exhaustion — 5 scenarios of pure noise; (B) model-output-unparseable events (malformed/empty JSON, think-only responses) that hit **no-retry paths** in the classify/batch phases, 3 scenarios; (C) fixture-graph/harness-conversion validation errors (subgraph expansion, dangling UI links, ambiguous reroutes) where the scenario is **structurally unpassable** and the model was never fairly tested, 5 scenarios — these are mis-graded; and (D) one mixed case (wanvideowrapper-1745) where a real model edit error (`unknown_target_field`, batch rolled back) is entangled with a local worker tempfile crash. Cross-run evidence confirms noise: gh-comfyui-7699 failed twice on a setup stall in threaded-59 but **passed** in mh-59; scenarios 1332 and 1644 failed in both runs but with a *different failure class each time* (classify-parse in mh-59, fixture validation in threaded-59) — the failure follows the harness, not the model. Every failed scenario is currently scored with `excluded_from_semantic_product_rates: false`, so roughly 14 fail-slots of noise are deflating the headline pass rate.

## Per-class analysis

### A. Provider/account transient (5)
Timeouts at classify/batch, one "provider temporarily unavailable", two OpenRouter credit-exhaustion rejections, and one scenario child that stalled in *setup* (before any executor phase) and was killed at the 300 s wall on both attempts. Nothing about the model's ability is observable. The strongest cross-run proof is `gh-comfyui-7699`: identical scenario, `success` in eval-mh-59, `infra_timeout` twice in eval-threaded-59. Two of these (950, 383) also burned successful batch turns before credit exhaustion hit — real work discarded. **Validity: 100 % noise.** **Fix:** credit pre-flight + retry budget + exclusion flag.

### B. Model-output unparseable / empty (3)
The two mh-59 `MalformedModelJSON` failures (`1332`, `1644`) are suspicious as harness artifacts: classify phase "failed" 4 ms after phase start with zero token usage and no raw response persisted — too fast for a live API round-trip, so the parse likely choked on a cached/empty/streaming-truncated payload rather than on real model output. The threaded `sageattention-403` is different and real: DeepSeek V4 Flash produced a 4.7k-token think block with no actionable content after a tool-call finish, and the harness surfaced it as ProviderError ("empty batch_repl response"). It also shows a tool-name mismatch (`web_search` unknown to the batch REPL), which pushed the model into reasoning-only mode. **Validity: mixed — treat the two classify failures as harness noise pending raw-response capture; the think-only case is a model-format signal that deserves its own metric, not a fail.** **Fix:** retry parse failures, persist raw payloads, reclassify think-only-empty away from ProviderError.

### C. Fixture-graph / harness-conversion validation error (5) — **mis-graded**
All five failed at the harness's UI→IR conversion *of the fixture*, before the model could deliver anything gradable:
- `workflow-templates-401` / `993`: the fixture's subgraph definition declares a `text` STRING input, but the canvas instance node has `widgets_values: []`; `native_subgraph_expansion` refuses ("missing instance widget for 'text'"). Both scenarios are `interaction_mode: answer_only` with `expect_graph_changed: false` — the model never needed to touch the subgraph at all, yet the expansion error blocked the entire run.
- `wanvideowrapper-403`: the **original fixture** contains node 72 with `inputs: [{link: 85, …}]` while the links array has no link 85 (link ids run 15–130). The fixture is malformed at rest.
- `wanvideowrapper-1332`: reported "UI link 1 references unknown endpoint '16'/'117'", but the request graph contains neither link 1 nor nodes 16/117 — the dangling reference is created inside the harness conversion, not present in the stored graph.
- `wanvideowrapper-1644`: reroute node 215 has an inbound link (330) but `outputs.links: null` (no downstream consumer); the virtual-wire resolver calls it ambiguous instead of treating it as a dead-end reroute.

**Validity: these are scenario defects; the fail verdicts are invalid measurements of the model.** All three threaded subgraph/link failures are answer-only scenarios, so a correct diagnosis would have been scored as a fail. **Fix:** pre-dispatch fixture validation using the same converter; repair or drop the fixtures; teach the converter to tolerate empty instance widgets and dangling/dead-end reroutes the way ComfyUI itself does.

### D. Mixed infra + genuine edit error (1)
`wanvideowrapper-1745` (mh-59) is the only failure containing real model signal: the batch phase produced edit statements targeting an unknown field (×2), which rolled back the whole batch — a genuine editing mistake against the node schema. But before retry, the agent worker process died on a `tempfile.NamedTemporaryFile` directory error, and the run was recorded as ProviderError with graph unchanged. The assessment then stacked `graph_changed`, `intent_judge`, and two `hard_diagnostic` issues on top of an infra corpse. **Validity: the unknown-target-field errors are signal worth counting in a model-edit-quality metric; the rest of the issue cascade is noise.** **Fix:** harden the worker temp-dir handling; preserve batch-rollback evidence as gradable even when a later infra failure kills the turn.

| Scenario (run) | Flag | Why |
|---|---|---|
| `workflow-templates-401`, `workflow-templates-993` (threaded) | **Mis-graded — scenario defect** | Answer-only scenarios blocked by harness's own subgraph expansion; correct diagnosis could never register |
| `wanvideowrapper-403`, `1332`, `1644` (threaded) | **Mis-graded — fixture/harness defect** | Validation errors originate in the fixture or the converter, not the model |
| `comfyui-7699` (threaded) | **Mis-graded — noise** | Setup stall; same scenario passed in eval-mh-59 |
| `950`, `sageattention-383` (threaded) | **Mis-graded — account noise** | OpenRouter credit exhaustion mid-run after real model work was done |
| `wanvideowrapper-1745` (mh) | **Partially mis-graded** | Genuine `unknown_target_field` edit error buried under an infra-crash issue cascade |

Cross-run corroboration: `1332` and `1644` appear as failures in **both** runs but under different classes each time (mh: classify parse; threaded: fixture validation) — the failure is a property of the pipeline, not the model. No scenario in this set is a confirmed genuine-reasoning failure; every "fail" verdict should be excluded from model-quality metrics until classes A–C are fixed.
