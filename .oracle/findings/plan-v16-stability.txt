COMPLETE NORTH STAR:

# North Star — one canonical Astrid pack

Astrid has one understandable pack concept. Every bundled product extension is
owned by one strict `pack.yaml`; a pack may contribute capabilities, SQLite
schema, agent documentation, or any combination. `timeline`, `shots`,
`references`, and `runaway` are ordinary bundled packs rather than a second
schema-pack species.

Opening a pack directory should reveal one authoritative declaration of its
identity, resources, custom capabilities, database ownership, migrations,
events, commands, CLI surface, and agent guidance. Runtime systems consume
typed projections of that declaration instead of independently rediscovering
or reinterpreting the pack. Every existing bundled customization is either
owned by a canonical pack or explicitly classified as irreducible kernel
behavior; nothing remains unclassified.

## Enduring principles

- One pack identity, manifest grammar, parser/validator, normalized definition,
  and bundled catalog.
- SQLite remains the per-project authority. Migration SQL owns columns,
  constraints, indexes, and transformations; YAML does not duplicate DDL.
- Reuse the strong machinery already present: typed registries, migration
  ordering/checksums/drift/transactions, `DatabaseWriter`, `UnitOfWork`,
  repositories, SDK behavior, and conformance tests.
- Bundled trusted packs may contribute database schema; external packs remain
  capability-only during beta.
- Every pack-relative resource is confined, discoverable, and present in the
  built wheel.
- Every user/agent-facing bundled pack ships structured agent documentation;
  the `_core` skill exposes a generated canonical pack census and routes agents
  to the owning pack documentation.
- With no users to migrate, cut directly to the final form and delete alternate
  authorities instead of maintaining shims.
- Keep beta scope proportionate: unify today's bundled system without
  prebuilding a marketplace or variable project-composition lifecycle.

## Anti-patterns

- Hiding the old schema-pack subsystem inside `pack.yaml` while retaining its
  parser, identity, discovery, or hard-coded standard list.
- Replacing useful typed registries with a giant universal service locator.
- Duplicating SQLite DDL or mutable runtime facts in YAML or skill prose.
- Per-project pack locks, enable/disable/purge state machines, dynamic database
  plugins, or migration ceremony without an observed beta need.
- Allowing external packs to execute SQL.
- Making the irreducible kernel dynamically unloadable for conceptual symmetry.
- Compatibility shims, dual reads, schema-less manifests, or legacy fallbacks.
- Declaring success while any bundled customization, documentation surface,
  operational consumer, or packaged resource bypasses canonical ownership.

## 3. Nested shapes

### `content`

Each key is an optional `RelativeDir`:

```yaml

  orchestrators: orchestrators
  elements: elements
  schemas: schemas
  examples: examples
  docs: docs
```

There is no fallback tree scan. Executor, orchestrator, and element roots use existing typed component loaders. Schema, example, and documentation roots recursively classify their contents.

### `permissions`

```yaml
    reason: Runs ffmpeg.
    access: Optional access description.
    services: [service_name]
```

Rules:

- `id` is one of `project_files`, `network`, `subprocess`, `environment`, `accelerator`, or `external_services`.
- `reason` is required `NonBlankText`.
- `access`, when present, is `NonBlankText`.
- Services are trimmed, duplicate-free `NonBlankText`.
- Duplicate permission IDs reject.

| `migrations` | Non-empty `Migration[]` |
| `stream_types` | Unique `DottedVocabulary[]` |
| `event_kinds` | Unique `DottedVocabulary[]` |
| `command_kinds` | Unique `DottedVocabulary[]` |
| `repositories` | Unique `RepositoryId[]` |
| `conformance` | Unique `LowerIdent[]` |
| `cli_mounts` | Map from `LowerIdent` to one or more single-space-separated `LowerIdent` tokens |
| `bridge_mounts` | Unique `LowerIdent[]` |

Each migration contains exactly:

- Positive integer `version`, unique within the pack.
- Unique `MigrationName` `name`.
- Unique `RelativeFile` `path` ending in `.sql`.
- Non-empty unique `LowerIdent[]` `tables`.

Migration descriptors appear in strictly increasing version order. A table has one owning pack globally. The migration first creating a table records ownership; later owner-pack migrations may alter it without reclaiming it. The four converted beta packs retain their current single initial migrations and SQL bytes.

YAML never contains columns, indexes, constraints, transformations, checksums, applied state, or a mutable head.

## 4. Normalization and immutable model

One parse produces a manifest-derived `PackDefinition` containing no root, source, trust, install state, manifest path, or raw mapping.

Normalization:

- Strip outer whitespace from prose and disclosure strings.
- Require identifiers in canonical case; never lowercase silently.
- Convert paths to canonical POSIX-relative strings.
- Preserve declared order only for `agent.normal_entrypoints` and migrations.
- Require increasing migration order.
- Reject duplicates and lexically normalize set-like lists.
- Sort mapping keys.
- Recursively freeze arbitrary JSON only in `generation.backends[].init_kwargs` and `extensions.schemas`.
- Make definitions, nested declarations, catalog entries, provenance, resource handles, database projections, admission projections, and snapshots frozen slot-based values.
- Serialize only normalized manifest data; roots and trust are never manifest fields.

```text
CatalogEntry
├── definition: PackDefinition
├── provenance: CatalogProvenance
├── manifest: ResourceHandle
├── resources: tuple[ResourceHandle, ...]
└── authoring_exclusions: tuple[AuthoringExclusion, ...]
```

Resource handles record owner-relative path, resolved root, role/kind, size, and SHA-256. Authoring exclusions remain declarations rather than handles.

Define:

```text
normalized_manifest_digest =
  SHA-256(canonical JSON(normalized PackDefinition))
```

This is distinct from:

- The raw `pack.yaml` resource-handle digest.
- `provenance_identity`.
- Migration checksums.
- Runtime-resource receipts.

## 5. Required fixtures

Golden fixtures:

1. Capability-only with executor content, permission, documentation, and no database.
2. Database-only with complete database fields and documentation.
3. Combined references-style content/database/SDK/CLI/documentation declaration.

Invalid fixtures cover:

- Missing, string, float, boolean, or non-2 schema version.
- Alternate manifest filenames, schema-less YAML, flat parser input, arbitrary manifest paths, and `schema-pack.yaml`.
- Owner-directory/ID mismatch and invalid release versions.
- Every unknown top-level and nested field class.
- Every prohibited v1 field.
- Null optional values.
- Duplicate set-like values.
- Alias ownership violations and deprecated alias fields.
- Malformed permissions and documentation unions.
- Bundled `documentation.kind: none`.
- Absolute, backslash, empty, traversal, symlink, missing, wrong-kind, or duplicate runtime paths.
- Supplemental/typed duplication.
- Source authoring-resource overlap or missing authoring path.
- Authoring-only paths present in a wheel.
- External `database`.
- Missing dependency, capability-only dependency, invalid minimum head, self-dependency, cycle, and duplicate dependency.
- Unordered/duplicate migrations, duplicate table ownership, and non-SQL paths.
- Provenance spoofing.
- Undeclared bundled non-Python files.
- Unowned, multiply owned, or unjustified bundled Python modules.
- Wheel-only/source-only runtime resources or Python modules.
- Legacy-only and canonical-plus-legacy bundled directories.
- Manifestless direct bundled children.
- Strict installed-record failures for pre-v2, missing-field, unknown-field, default-dependent, and unknown-version records.

# III. Catalog construction, provenance, installed admission, and lifetime

## 1. Bundled catalog discovery is closed over direct children

Build one immutable `BundledCatalog` from the source or installed `astrid/packs` package root.

Enumerate every direct child directory in lexical order without following symlinks.

For each child:

1. If its name is `_core`, require it to be the sole explicit non-pack kernel guidance directory. Validate its expected skill/documentation shape separately.
2. Every other direct child is required to be a product pack.
3. Inspect the child root for exact basenames:
   - `pack.yaml`
   - `pack.yml`
   - `pack.json`
   - `schema-pack.yaml`
4. Reject if any legacy basename exists, whether or not `pack.yaml` also exists.
5. Reject if `pack.yaml` is absent.
6. Parse `pack.yaml` exactly once, enforce v2 and owner-directory/ID equality, normalize it, validate mandatory structured documentation, resolve admitted runtime resources, and construct its immutable entry.
7. Reject duplicate IDs or an unloaded direct child.
8. Require the sorted direct-child names excluding `_core` to equal the sorted loaded owner-directory names and loaded pack IDs.

The reviewed final retained set is exactly:

```text
blender
comfy_wrap
editorial
fal
foley
generation
iteration
media
moirae
references
reigh
rendering
runaway
runpod
shots
stream_content
timeline
training
understanding
vibecomfy
video_editing
youtube
```

The runtime catalog does not use this list as an allowlist. WP0 freezes it as the expected beta source-layout audit fixture, and the executable audit compares:

- Direct filesystem children.
- Loaded owner directories.
- Loaded pack IDs.
- Reviewed expected retained names and count.
- Source/wheel child and catalog sets.

A missing, extra, manifestless, legacy-only, duplicate, or unloaded direct child fails.

Cache the bundled catalog once for the process/package-root lifetime. It contains declarations and resource handles only—never connections, repositories, CLI parsers, bridges, capability instances, services, or application objects.

## 2. Root-independent provenance identity

Every parsed candidate receives:

```text
SHA-256(
  UTF-8 canonical JSON {
    "schema": "astrid.pack_provenance.v1",
    "definition": <normalized PackDefinition>,
    "declared_paths": [
      {"path": <owner-relative POSIX path>, "role": <typed role>}
    ]
  }
)
```

Canonical JSON uses sorted keys, no insignificant whitespace, UTF-8, JSON boolean/null rules, and arrays already normalized by the manifest contract.

`declared_paths` includes every path directly declared by:

- `content`.
- Rendering extensions.
- Database migrations.
- Documentation.
- `agent.required_context`.
- Supplemental resources.
- Authoring-only declarations.

It excludes absolute roots, checkout paths, installation paths, discovery order, provenance class, rejected diagnostics, resource bytes, and mutable installation state.

Uses:

- Candidate key: `<pack_id>@<provenance_identity>`.
- Source/wheel comparison requires equal identity plus independent runtime-resource and Python-module comparisons.
- Duplicate handling compares identity and exact resource receipts.
- Diagnostics use the same candidate key.
- External-database rejection can compute identity after normalization and before SQL/resource access.
- Installed v2 admission records bind to this identity.

Two candidates with equal provenance identity but different resource receipts are not identical duplicates.

`CatalogProvenance` contains:

- Provenance class.
- `provenance_identity`.
- `normalized_manifest_digest`.
- Optional diagnostic root/revision details.
- Captured installed admission disposition where applicable.

Manifest fields cannot set or override provenance.

## 3. Dynamic candidate capture and precedence

Each top-level operation captures dynamic candidates once from:

1. Project-local packs.
2. Explicit extra roots in caller order.
3. `ASTRID_PACKS_PATH` roots in environment order.
4. Installed active revisions sorted by pack ID.

Within a root, sort candidates by pack ID and canonical manifest path.

Precedence:

```text
bundled > local > explicit-extra > environment > installed
```

Duplicate policy:

- Bundled IDs are reserved and always win.
- Candidates with the same pack ID, provenance identity, and exact resource receipts deduplicate.
- Same ID with differing identity or receipts produces a `duplicate_id` loser diagnostic containing winner and loser provenance.
- A losing candidate contributes nothing.
- Invalid external discovery may be recorded while other discovery continues, preserving current fault isolation.
- Direct validation or installation of the rejected candidate is a hard error.

Read-only discovery never creates `astrid/packs/local`; only explicit create or fork operations may do so.

## 4. External database fail-closed boundary

After structural normalization and provenance assignment, any non-bundled candidate containing `database` rejects as `external_database_forbidden`.

Rejection occurs before:

- Resource resolution.
- SQL reads.
- Migration projection.
- Capability or alias projection.
- Permission admission.
- Installation publication.

The entire candidate rejects; the database block is never stripped.

Tests cover local, explicit-extra, environment, Git-installed, and installed-revision candidates.

## 5. Strict installed record v2

Replace permissive `InstallRecord.from_dict()` behavior with one exact v2 parser. Unknown keys, missing fields, wrong types, nulls, silent defaults, schema versions other than 2, and legacy records reject.

The v2 record contains exact typed fields:

```text
InstallRecordV2
├── record_schema_version: integer exactly 2
├── pack_id: PackId
├── pack_name: NonBlankText
├── pack_version: ReleaseVersion
├── revision_identity: NonBlankText
├── installed_at: normalized UTC timestamp
├── source: InstalledSource
├── provenance_identity: lowercase SHA-256 hex
├── normalized_manifest_digest: lowercase SHA-256 hex
├── accepted_permissions: tuple[NormalizedPermission, ...]
└── validation: InstalledValidation
```

`InstalledSource` is a strict tagged union:

```text
local:
  kind: local
  diagnostic_origin: NonBlankText

git:
  kind: git
  git_url: NonBlankText
  commit_sha: exactly 40 lowercase hexadecimal characters
  requested_ref: NonBlankText
```

`diagnostic_origin` is informational and never authorizes trust.

`InstalledValidation` has exact fields:

```text
disposition: accepted | rejected
validated_at: normalized UTC timestamp
reason_codes: tuple[LowerIdent, ...]
```

Rules:

- A revision is executable only when its record is exact v2 and `validation.disposition == accepted`.
- Successful installation publishes a fresh accepted v2 record only after canonical validation, external-database rejection, permission acceptance, manifest/resource verification, and staged-copy verification.
- Rejected validation is not published as the active revision. A retained rejected record may be inspectable as history but cannot contribute capabilities.
- Active state remains owned by the store’s active-revision pointer; it is not duplicated by an `active` field in the record.
- `revision_identity` is the store-owned revision identifier and must agree with the selected revision directory.
- `provenance_identity` and `normalized_manifest_digest` must agree with the canonical candidate parsed from that selected revision.
- `accepted_permissions` is the exact normalized permission tuple accepted for that revision and must exactly cover the immutable candidate declaration.
- Remove persisted component inventories, entrypoint summaries, derived secrets/dependencies, raw trust summaries, mutable trust tiers, and other facts that canonical parsing can project.
- Inspect-only source metadata may remain only in the strict `source` union above.
- Remove raw-manifest trust reparsing from installation and discovery.
- Remove old-record field filtering and every missing-field default.
- Pre-v2, incomplete, malformed, or unknown-version records yield deterministic `installed_record_v2_required` / `reinstall_required` diagnostics.
- There is no old-record migration, lazy rewrite, default shim, fallback trust summary, fallback validation, or automatic reinstallation.

Golden external tests always install fresh v2 records.

## 6. Capture-time installed admission

`InstalledPackStore` remains the sole installed-state and admission owner. It emits an immutable `ExternalAdmissionDisposition` while the top-level snapshot is constructed.

```text
ExternalAdmissionDisposition
├── inspectable: bool
├── executable: bool
├── reason_codes: tuple[str, ...]
├── revision_identity: optional str
├── provenance_identity: optional str
├── normalized_manifest_digest: optional str
└── accepted_permissions: tuple[NormalizedPermission, ...]
```

For an installed candidate, the captured admission binding is:

```text
(
  pack_id,
  revision_identity,
  provenance_identity,
  normalized_manifest_digest,
  accepted_permissions,
  validation_disposition
)
```

The store performs one coherent store-owned capture:

1. Resolve the active revision.
2. Strictly parse its v2 record.
3. Confirm record pack/revision identity.
4. Canonically load the candidate once.
5. Confirm record provenance identity equals candidate provenance identity.
6. Confirm record normalized manifest digest equals the canonical definition digest.
7. Confirm accepted permissions exactly cover the candidate’s normalized permission declaration.
8. Confirm validation disposition is accepted.
9. Confirm the candidate has no `database`.
10. Capture the manifest handle and admitted resource handles.

The store may use its existing narrow per-pack synchronization to obtain a coherent read while capturing these facts. No lock is retained after snapshot construction and no lock is held across pack execution.

Source policy:

| Source | Inspect | Capability execution | Database |
|---|---:|---:|---:|
| bundled | yes | yes | yes |
| local | yes | yes | no |
| explicit extra | yes | yes | no |
| environment | yes | no | no |
| installed | yes | only when capture-time v2 admission succeeds | no |

An installed pack declaring no permissions requires an exact empty accepted-permission tuple.

Missing or mismatched evidence produces inspect-only disposition with deterministic reason codes. It never falls back to executable.

Every external capability consumer—executor, orchestrator, rendering, generation, SDK, or other registry—uses this single captured projection. Consumers do not reparse manifests or implement another trust policy.

## 7. Superseded Wave 4 behavior: no pre-use store-state check

After snapshot capture:

- The selected installed revision remains admitted for that operation lifetime.
- Activation, rollback, invalidation, record replacement, or permission-receipt changes affect the next top-level operation.
- Current execution does not reread the active pointer or install record.
- Current execution does not switch revisions or update its admission disposition.
- No store check is inserted immediately before capability invocation.
- No lock spans capability execution.
- No revocation service, retry, rediscovery, snapshot replacement, or alternate-revision selection is added.

Immediately before external capability execution, verify only:

1. The captured raw manifest `ResourceHandle`.
2. The captured resource handles consumed by the selected capability projection.

A missing, changed, wrong-size, or wrong-digest captured manifest/resource fails closed before pack code runs.

Store-only mutations after capture do not invalidate the current operation’s admitted capability. Physical mutation/removal of the captured manifest or consumed resources does fail the handle check.

Required concurrency/lifetime tests:

- Capture revision A, activate B, and prove the existing operation still selects A.
- A later operation sees B.
- Capture A, mark its store record invalid/rejected, and prove the existing operation still selects A when captured files are intact.
- A later operation refuses A.
- Capture A, replace its accepted-permission record, and prove the existing operation retains its captured admission.
- A later operation evaluates the replacement record.
- Change the captured manifest after capture and prove use fails closed.
- Change or delete a consumed resource after capture and prove use fails closed.
- Mutate an unconsumed external resource and prove no broad rescan occurs.
- Prove no execution path rereads store admission state, retries, or switches revisions.

## 8. Snapshot construction

```text
CatalogSnapshot
├── bundled_catalog
├── entries_by_id
├── ordered_entries
├── rejected_candidates
└── construction_context
```

There is deliberately:

- No `snapshot_fingerprint`.
- No whole-snapshot identity.
- No hashing of rejected diagnostics.
- No global layer-order hash.
- No retry-on-change system.
- No general stale-handle scan.

`construction_context` is diagnostic-only and may retain local roots/order. It is excluded from source/wheel semantic comparison and operation-receipt identity.

## 9. Lifetime and freshness contract

One snapshot governs:

- One CLI invocation.
- One standalone `sdk.discover`, `get_capability`, or `invoke` call.
- One `AstridClient.open()` lifetime.
- One standard application lifetime.
- One serve lifetime.
- One doctor run.
- One inspect command.
- One backup create or restore validation.
- One install validation/admission.
- One source or package audit.

Consumers cannot rescan or reconstruct a snapshot internally. Convenience APIs create one only at a top-level boundary. Registries accept the snapshot or narrow typed projections.

Bundled lifetime:

- Bundled catalog is immutable for the process/package-root lifetime.
- Production performs no recursive rescan, cache invalidation, global fingerprint comparison, or broad stale-handle verification.
- Changing bundled files requires a new process/catalog lifetime.
- Tests mutating fixtures explicitly end the old lifetime and use a narrow test factory/cache-clear seam.
- Migration checksum verification remains existing database safety, not catalog freshness machinery.

Dynamic external lifetime:

- Candidates and installed admission are captured once per top-level operation.
- External manifest and resource handles retain captured size/digest receipts.
- Security-sensitive use verifies the captured manifest and only the consumed resource handles.
- Installation verifies the manifest and all admitted resource handles before publication.
- Direct resource validation verifies the handles it consumes.
- A handle mismatch fails closed without retry, rediscovery, snapshot update, or candidate replacement.
- Inspection-only operations do not perform broad resource reverification.
- External filesystem changes become visible to later operations.
- Installed store-state changes become authoritative to later operations.

# IV. Bundled resource and Python ownership closure

## 1. Exact inventory exclusions

Walk each bundled source pack deterministically without following symlinks. Reject every symlink before classification.

There is no generic cache/build exclusion and no skipped subtree.

Python source is handled separately:

- Regular files ending exactly in `.py` enter the Python ownership audit in §IV.4.
- They are excluded from non-Python package-data equality.
- Other Python/runtime artifacts are not covered by this exclusion.

The only audit-noise allowlist is:

1. A regular file whose exact basename is `.DS_Store`.
2. A regular file whose owner-relative path matches:

```regex
(?:^|/)__pycache__/[^/]+\.py[co]$
```

Rules:

- No directory is skipped wholesale.
- A non-bytecode file under `__pycache__` is inventoried normally.
- `.pyc` or `.pyo` outside an immediate `__pycache__` is inventoried normally.
- `.gitignore`, `.gitkeep`, generated output, build directories, test data, editor metadata, requirements, services, templates, schemas, docs, fonts, and all other files are not implicitly excluded.
- Intentional source-only content uses `authoring_only`.
- Unexpected cache/build artifacts fail as undeclared or prohibited content.

Every remaining regular non-Python file must have exactly one classification:

- Typed runtime reachability.
- Supplemental runtime declaration.
- Authoring-only declaration.

Zero classifications is `undeclared_file`; multiple classifications is `duplicate_classification`.

## 2. Typed resource reachability

- Executor, orchestrator, and element roots use existing typed validators instead of claiming directories blindly.
- Component manifests, schema-declared paths, `STAGE.md`, assets, and documentation routes create resource edges.
- Schema, example, and documentation roots recursively classify files.
- Renderer, planner, and finalizer declarations classify their manifests and typed path fields.
- Migration paths classify SQL.
- Documentation and `agent.required_context` classify documents.
- Supplemental directories expand recursively.
- Nested skills, requirements, templates, services, and opaque assets must be reached through typed or supplemental declarations.
- Empty runtime-resource directories reject.
- Each physical file may be reached by exactly one declaration path.

## 3. Targeted runtime-use audit

Scan runtime Python below bundled pack roots.

Recognize:

- `open`.
- `Path.open`, `read_text`, and `read_bytes`.
- `importlib.resources.files`, `open_text`, and `open_binary`.
- `pkgutil.get_data`.
- Simple literal `Path(__file__)` and `__file__` composition using `/`, `joinpath`, `with_name`, and `parent`.
- Existing executor requirements-file probing.
- Blender service-unit lookup.
- Existing typed component and rendering resource APIs.

Use only intra-module propagation of simple literal assignments. Do not attempt general analysis of generated paths, project paths, user input, or network resources.

Every statically resolvable pack-relative runtime read must enter runtime-resource closure. A resolvable cross-root read must move into its owner or resolve through a justified kernel-owned resource recorded in the coverage ledger.

Migration SQL, component manifests, `STAGE.md`, `SKILL.md`, `requirements*.txt`, referenced schemas/templates, services, and runtime assets cannot be authoring-only.

## 4. Complete Python ownership audit

Python remains governed by ordinary module packaging, not the non-Python `resources` grammar.

The coverage inventory enumerates every `.py` file beneath every retained bundled pack root and derives its canonical module name. Each module must have:

- Exactly one physical owner, determined by its pack root.
- Exactly one justified ownership route.
- Source and installed-wheel import-origin evidence.

Valid ownership routes are:

1. The module lies beneath a manifest-declared typed `content` subtree.
2. The module implements a manifest-declared typed extension whose canonical registry/module mapping points to it.
3. The module implements a manifest-declared database surface—repository, command, vocabulary, conformance, CLI, or bridge—proven by exact registry/import/AST evidence.
4. It is an exact `__init__.py` package-initialization module with a recorded, nonblank initialization role and no independent unclassified customization.

Rules:

- Directory location alone establishes physical ownership but not contribution reachability.
- Wildcard “all Python in this pack” claims are invalid.
- A module reachable through more than one conflicting contribution route fails as multiply owned.
- A module with no route fails as unclassified.
- A package initializer containing substantive registrations or behavior must be mapped to those declared surfaces; the initializer exception cannot hide customization.
- Pack-local test or development Python that is not a shipped contribution must move to the normal test tree rather than being smuggled through package initialization.
- No Python file is added to `resources` solely to satisfy package-data closure.
- Installed-wheel validation compares the logical bundled module set and proves imported module origins lie beneath the isolated wheel environment.
- Any source module absent from the wheel, unexpected wheel-only module, source-origin import, multiply owned module, or unclassified module fails.

Coverage adds:

```text
python_module:<pack_id>/<canonical_module_name>
```

with exact source path, ownership route, manifest surface IDs, consumers, and installed origin evidence.

## 5. Source/wheel equality

Each non-Python audit emits sorted resource records:

```json
{
  "pack_id": "blender",
  "path": "server/blender-render-api.service",
  "kind": "service",
  "size": 1234,
  "sha256": "..."
}
```

Require equality of:

- Direct bundled child sets.
- Loaded pack IDs.
- `provenance_identity`.
- `normalized_manifest_digest`.
- Normalized definitions, including authoring-only declarations.
- Runtime-resource paths, roles, sizes, and hashes.
- Database declarations and derived heads.
- Documentation routes.
- Bundled provenance class.
- Logical bundled Python module sets.

Also require:

- Every source authoring-only path exists.
- No authoring-only path exists in the wheel.
- No undeclared non-Python bundled file exists.
- Every bundled Python module has one valid ownership route.
- Every installed bundled Python import resolves beneath the isolated wheel.
- Absolute roots are never compared.

Use existing setuptools package-data and normal Python module packaging. Add no packaging backend.

# VI. Database composition and migrations

## 1. Projection

Select:

- A synthetic code-owned `core` node at migration head 1.
- Every snapshot entry with bundled provenance and a `database` contribution.

No pack allowlist, standard tuple, expected-name branch, or schema-pack identity participates.

A synthetic trusted bundled database pack introduced in a test snapshot must enter composition without composition-code changes.

Each node contains ID, immutable declaration, owner resource handles, derived head, provenance, and existing collision projections.

## 2. Dependency semantics

For node `P`:

```text
head(P) = max(P.migrations[].version)
```

`depends_on: {pack: Q, min_migration: N}` means:

- `Q` is a selected database node or `core`.
- `head(Q) >= N`.
- All migrations of `Q` precede all migrations of `P`.
- It does not compare release versions or inspect applied project state.

Before database open, require:

- Every database pack has a direct or transitive path to `core`.
- No self-dependency.
- No duplicate dependency target.
- Every target has migrations.
- Every minimum is positive and no greater than target head.
- The graph is acyclic.
- Existing table, migration identity/name, vocabulary, repository, CLI, bridge, and other collision checks pass.

## 3. Expected bundled fixture and ordering

Converted manifests are expected to project:

```text
core@1
├── references@1  requires core >= 1
├── runaway@1     requires core >= 1
├── shots@1       requires core >= 1
```

# Megado

Plan → explore → revise → execute → oracle-gate → sync, all in a worktree, never on main.

- **Planner** — GPT-5.6 Sol (codex exec, high reasoning): tasklist, revision, batch design.
- **Plan sense-checkers** — independent DeepSeek V4 Flash or GPT-5.6 Luna subagents: challenge simplicity, scope, abstractions, sequencing, and verification before the plan freezes.
- **Explorer / normal Executor** — DeepSeek V4 Flash or GPT-5.6 Luna, selected by the user's run declaration.
- **Oracle / sense checker** — GPT-5.6 Sol or Grok 4.6 (grok CLI): gates every batch, finalizes normal versus `[XHARD]` classification, applies the user's model declaration, and decides what rework is actually required.
- **`[XHARD]` Executor** — GPT-5.6 Sol or Grok 4.6, reserved for exceptionally hard tasks and selected by the user's run declaration.

One orchestrator (the host) drives all phases, holds the `.oracle/` artifacts, and writes every brief. Automatic routing may move between eligible models; a user-pinned model requires user approval before any switch.

## Declare models for this run

At the start of every run, before freezing the goal or dispatching any model, show the user the task classes and eligible models:

- **Normal tasks:** DeepSeek V4 Flash or GPT-5.6 Luna.
- **`[XHARD]` tasks (exceptional and rare):** GPT-5.6 Sol or Grok 4.6.

Ask the user to specify the normal-task model and the `[XHARD]` model for this run. Also offer **automatic per-task selection** for either class if the user wants the run's judgment owner to choose case by case. If the user already specified the choices in the request, restate and record them without asking again.

Write the resulting declaration into `.oracle/agent_goal.md`. A user-selected model remains authoritative for that class unless the user changes it. If it is unavailable or demonstrably unsuitable, report the evidence and ask before switching. Under automatic selection, the judgment owner may choose either eligible model per task and records the choice and rationale.

## North Star, agent goal, and source custody

Before planning, create or adopt `.oracle/northstar.md`, then freeze `.oracle/agent_goal.md`. The agent goal must link to the North Star with `[North Star](./northstar.md)`.

**`northstar.md` is the durable direction.** Keep it succinct—normally one page or less. It explains:

- the desirable end state in plain language;
- the enduring qualities, principles, or invariants the work should preserve;
- the important anti-patterns, failure modes, and hollow versions of success to avoid;
- what aligned progress should feel or look like across multiple batches or runs.

The North Star is not a task list, acceptance checklist, source manifest, validation plan, or authorization document. It should not contain run-local implementation detail. If a durable project North Star already exists, snapshot or copy it into `.oracle/northstar.md` and record its source path and digest in custody rather than casually rewriting it.

**`agent_goal.md` is the frozen operational contract for this run.** It records:

- the concrete objective and end-state contribution for this agent;
- the North Star link plus one sentence explaining how this run advances it;
- authoritative inputs and immutable source ref;
- in-scope work, non-goals, settled decisions, and open boundaries;
- authorization boundaries, including mutation, sync, promotion, and deployment;
- the user-declared model policy;
- exact done and stop criteria;
- final validation commands and scenarios;
- sync/promotion policy.

The North Star provides alignment, never authority: it cannot widen the agent goal's scope, permissions, or done criteria. If the documents conflict, stop and reconcile the conflict with the user rather than choosing one silently. The plan may evolve within the agent goal; it must not silently change either document. Changing the North Star requires explicit user agreement and a fresh review of `agent_goal.md` against it.

**North Star propagation is mandatory.** Every model-facing unit of work—planning or revision prompt, settled-plan sense-check brief, exploration brief, task or rework item, executor brief, validation brief, routine check-in, cumulative big-batch review, re-review, and final overall review—must receive the complete contents of `.oracle/northstar.md`, not merely a path or link. Every task record names the relevant North Star principle or anti-pattern, or explicitly says that none is task-specific. Every execution brief instructs the model to advance the stated end state and avoid the named anti-patterns without widening `agent_goal.md`; every review verdict includes an explicit North Star alignment disposition. Record the North Star digest in every invocation receipt so the run can prove which version each model saw. If the North Star changes, do not let pending work silently inherit it: re-review `agent_goal.md`, regenerate affected briefs, and freshly review affected open tasks.

Before creating the worktree or mutating anything, record a source-custody baseline: HEAD and explicit source ref, branch, status, untracked files, all worktrees, remotes/refs, environment identity, and protected local work that must survive. Keep that baseline with the run and identify the base SHA in every receipt.

> **Keep in sync with `microdo`.** These two skills share the delegation mandate, the roles table, invocation flags, and gotchas. If you edit this skill, apply the same change to `microdo/SKILL.md` — and vice versa. Keep the shared blocks identical.

## Execution model routing

The skill fixes the **eligible pools**, not the exact model:

- **Normal tasks:** DeepSeek V4 Flash or GPT-5.6 Luna.
- **`[XHARD]` tasks:** GPT-5.6 Sol or Grok 4.6.

The user's declaration controls assignment. If the user selected a model for a class, use it for that class. If the user selected automatic routing, the run's judgment owner—the oracle in Megado, the integrator in Microdo—first classifies the task, then selects one eligible model based on task fit, context continuity, tool needs, and current model availability or health. Record the classification, selected model, and rationale (`user-selected` or the automatic-routing reason) in the tasklist or rework tasklist and invocation receipt. Never treat a previous task's model as a default unless the user's declaration fixed it for the run.

## `[XHARD]` threshold

**Normal is the default. `[XHARD]` is an exceptional classification for extremely hard work; many runs should have no `[XHARD]` tasks at all.** First decompose the work into clear, bounded tasks. Classify only the irreducible remainder as `[XHARD]`, and only when the judgment owner can show that:

- it requires sustained, subtle reasoning or novel judgment across tightly coupled concerns;
- a plausible mistake could survive ordinary local validation and cause non-local or hard-to-detect harm; and
- neither DeepSeek V4 Flash nor GPT-5.6 Luna can be expected to execute it reliably from a precise mechanical brief.

Size, file count, importance, unfamiliarity, cross-cutting scope, write volume, time pressure, or one failed normal-model attempt do **not** make a task `[XHARD]` by themselves. Diagnose brief quality, environment, tools, and decomposition before escalating. Prefer keeping tractable subparts normal and assigning only the genuinely irreducible judgment kernel to `[XHARD]`. When uncertain, classify the task as normal.

Every `[XHARD]` tag requires a concrete written rationale stating why decomposition is insufficient and why the normal pool is not reliable for this specific task. A label without that evidence must be rejected by the oracle/integrator.

## Delegation mandate — verbatim in every oracle check-in brief and `[XHARD]` task brief

> DELEGATION MANDATE — You are a manager and validator of the normal execution pool, NOT a worker. Delegate as much as possible to the task's selected normal model: DeepSeek V4 Flash or GPT-5.6 Luna. Flash invocation: `omp -p @<brief>.md --model deepseek-v4-flash --cwd <worktree> --no-session --auto-approve --max-time=1800`; Luna invocation: `launch_hermes_agent.py --model="codex:gpt-5.6-luna" --query-file=<brief> --project-dir=<worktree>` (research-only briefs use read/search tools). Dispatch research, execution, and critique briefs to the selected model — critique passes optimize for elegance: KISS, YAGNI, cut scope that isn't pulling its weight; flag overengineering, not just bugs. Your job is to direct, then validate: read delegated output against the acceptance criteria; do work yourself only when delegation is impossible — the selected normal model already failed at it, or the piece is too small / too tightly coupled to your own reasoning to hand off. If you catch yourself implementing or researching directly, stop and ask whether a normal-pool brief would cover it. It almost always would.

## Oracle review count

Here, a **review pass** means one independent reviewer produces one verdict against the full acceptance criteria. The oracle's own synthesis and final `PASS`/issues judgment do not count as another pass.

The reserved pre-settled critique slot is not currently a review. Settled-plan sense-check waves are targeted critiques rather than full acceptance-criteria verdicts, so they do not count as Oracle review passes. They may not replace the fresh independent pre-execution contract review.

Use a cheap-to-expensive escalation for each segment (routine batch, cumulative boundary, or rework packet):

- **Segment review:** default to **three independent GPT-5.6 Luna** passes against the same frozen packet. They are separate verdicts, not a single panel or a synthesis of one another.
- **Expand only on evidence:** commission up to **five Luna** passes only when the initial passes disagree, a pass is unusable/inconclusive, or the evidence conflicts. Record the trigger and resolution. Do not spend a higher-cost review to rescue a known-broken candidate.
- **Rework gate:** any `REWORK` verdict blocks escalation and downstream work. After correction, create a fresh review packet bound to the new artifact identities and restart the segment review sequence; a prior reviewer process or verdict does not count for the corrected candidate.
- **Segment Sol oracle:** after Luna reaches convergence on `PASS`, commission at most **one GPT-5.6 Sol** oracle review for that segment, only when the segment's risk or the user's instructions warrant it. Sol reviews the same frozen identities and must not be used to bless an unresolved `REWORK`.
- **Final integrated panel:** once all segments pass, commission up to **nine independent GPT-5.6 Sol** passes for the whole deliverable when warranted by integration risk or explicit user direction. The panel synthesis is separate and does not add another pass.

These counts are defaults, not a license to widen scope: explicit user model or count choices control, and the existing model-routing and fallback rules still apply. Every pass must record the immutable source/checkpoint, brief, manifest, and diff identities it reviewed. The oracle records why it stopped at the selected count and why any escalation was proportionate.

## Huge-run periodic cumulative reviews

During planning, record the planner's best-effort estimate of total end-to-end implementation effort in `plan.md` and the current huge-run state in `status.md`. If it is **greater than two weeks**, mark the run as a **huge run** and activate periodic cumulative big-batch reviews. This is a review policy inside Megado; it does not by itself change the user's requested execution mechanism. If a run initially estimated at two weeks or less later grows beyond the threshold, activate the policy before executing the next batch and record the revised estimate and reason in both files. Do not mutate the frozen `agent_goal.md` merely to store sizing metadata.

For a huge run, the oracle uses judgment to predeclare cumulative review boundaries in `tasklist.md`. Choose the cadence from change volume, coupling, architectural risk, integration complexity, stability of prior batches, and the cost of discovering drift late; also place a boundary at any major architectural, integration, migration, or dependency seam. Record the rationale for the cadence. The oracle may move the next boundary earlier or later as evidence changes, but must record why in `status.md` and must not defer cumulative integration review until it is effectively only the final review. Routine per-batch and cumulative reviews use the segment policy above, and the cumulative reviews do not replace the final overall review.

Keep the run **maximally synchronous**. Parallelize genuinely independent work inside the current approved batch, but do not let dependent work or later batches run ahead on stale, incomplete, or unreviewed state. Every dispatch starts from the latest passed checkpoint and current North Star, goal, plan, tasklist, and accepted rework. As results land, promptly reconcile code, receipts, evidence, `execution.log`, and `status.md`; then run the required review and resolve accepted findings before dependent work continues. At a cumulative boundary, pause forward execution until the integrated state and documentation converge on one reviewed checkpoint and the gate passes. “Synchronous” means frequent convergence around authoritative state, not needlessly serializing independent tasks.

Each cumulative brief embeds the complete North Star and includes `agent_goal.md`, the stable plan and frozen tasklist, every completed batch check-in, all earlier cumulative-review verdicts, the cumulative diff from the run base through the current checkpoint, and the relevant receipts and evidence. The reviewer assesses the integrated system—not merely the latest delta—for cross-batch regressions, interface mismatches, architectural drift, missing goal coverage, stale assumptions, accumulating complexity, and North Star alignment or anti-patterns. The verdict is binary: `PASS` or a list of evidence-backed issues.

Store the immutable verdict as `.oracle/checkins/big-batch-<K>-through-batch-<N>.md`. The oracle sense-checks every finding. Accepted findings enter `.oracle/rework/big-batch-<K>-attempt-<M>.md` and follow the same tasklist → model classification → execution → fresh independent full re-review loop as batch rework. Do not start the next execution batch until the cumulative gate passes. Record the boundary, verdict, rework, evidence, and next cumulative boundary in `status.md` and `execution.log`.

## Phase 3 — Revise and sense-check until STABLE

First classify the current plan as **already settled** or **still forming**. A plan is already settled only when it is coherent end to end, its material decisions and dependencies are resolved, no material planning question remains open, and current exploration evidence does not unset it. Record the classification and evidence in `status.md`.

### Pre-settled critique wave — reserved

This stage is intentionally empty for now. Do not infer or invent its prompt, subagents, lenses, artifacts, cadence, or pass criteria. If the plan is already settled—including a supplied or adopted plan that meets the test above—record `skipped: already settled`. If it is still forming, record `reserved: not yet specified` and continue the ordinary explore/revise loop without pretending this placeholder ran.

Feed `.oracle/northstar.md` + `.oracle/agent_goal.md` + `.oracle/plan.md` + all relevant exploration findings to Sol:

> Update the plan given these findings while staying inside the agent goal and advancing the North Star. Explicitly reject any named North Star anti-pattern. Bias toward **elegance and simplicity** — cut scope that isn't pulling its weight. List any new areas to explore and potential issues. If nothing material changed, answer exactly `STABLE`.

New material areas → re-run Phase 2 for them, then revise again.

Once Sol says `STABLE`, run the **settled-plan sense-check wave** before accepting the plan. This is the streamlining and unnecessary-abstraction wave described below. The oracle chooses a useful set of independent normal-pool subagents and critique lenses according to the settled plan's size and risk; there is no fixed critic count or preset lens list. Use the user's declared normal model or authorized automatic routing.

All subagents in the settled-plan wave receive the exact same immutable plan snapshot and digest, plus the complete North Star, frozen agent goal, relevant exploration evidence, prior accepted findings and dispositions, and a narrow mechanical brief. Do not mix plan versions inside one wave. Run independent critics in parallel, then synthesize only after the whole wave returns.

Across the settled-plan wave, challenge whether:

- the outcome can be reached with less work, fewer steps, or fewer handoffs;
- the plan is maximally streamlined and understandable;
- any proposed abstraction, layer, interface, service, configuration surface, or generalization is speculative or unnecessary;
- existing mechanisms can be reused instead of creating parallel ones;
- batches, dependencies, and synchronization points form the simplest safe execution order;
- validation and documentation are sufficient but proportionate rather than ceremonial; and
- every retained element advances an agent-goal criterion and the North Star without reproducing an anti-pattern.

Critics identify and rank concrete simplifications with plan-section or source evidence; they do not widen scope, rewrite the plan, or invent architecture. Save each output as `.oracle/findings/plan-settled-<W>-<lens>.txt` with an invocation receipt. After every subagent in the wave returns, the oracle writes `.oracle/findings/plan-settled-<W>-synthesis.md`, deduplicating findings and recording `accept`, `reject`, or `investigate` with rationale. Feed accepted findings to Sol for a full-plan revision.

If a settled-plan finding materially reopens the plan, classify it as still forming and return to the ordinary explore/revise loop; the pre-settled slot remains unexecuted until its contract is defined. Once Sol says `STABLE` again, always run a fresh settled-plan wave on the entire revised plan, not merely the edited sections. The plan is finally settled only when Sol says `STABLE` and the latest complete settled-plan wave yields no accepted material simplification or unresolved investigation. If critics repeat a settled objection without new evidence, cite the prior disposition rather than looping indefinitely. Then continue to the independent pre-execution contract review in Phase 4.

## Phase 4 — Tasklist (Codex, read-only)

Convert the stable plan into `.oracle/tasklist.md`. The planner proposes classifications; the tasklist becomes **frozen only after** the pre-execution oracle check passes:

- **Sensible batches** — self-contained, ending at natural seams.

**4. Rework execution and re-review.** Generate executor briefs from the supplemental tasklist, embedding the complete North Star in every brief and preserving each rework item's alignment/anti-pattern instruction. Execute the normal and `[XHARD]` items with their assigned models, commit the revised batch, create a fresh packet bound to the revised artifact identities, and restart the segment review sequence under the Oracle review count policy. Repeat the triage → tasklist → execution → fresh-review loop until the oracle passes. Record each finding, tasklist, revision, result digest, actual model/provider, command, cwd, base/head SHAs, North Star digest, PID/timestamps/exit, and evidence paths. An implementer or revision agent never reviews its own work. **Do not start batch N+1 until batch N passes.**

**5. Huge-run cumulative gate.** When the current passed batch reaches a predeclared huge-run boundary, perform the periodic cumulative big-batch review before starting the next batch. Treat the cumulative boundary as its own segment: use the complete cumulative scope and artifacts required by Huge-run periodic cumulative reviews, start with three independent Luna passes, expand only on disagreement or inconclusive/conflicting evidence, and after Luna convergence may commission at most one Sol oracle pass when warranted. Any `REWORK` requires correction, a fresh packet, and a restarted review sequence; a routine batch pass cannot substitute for this gate, which must reach `PASS`.

## Validation and completion contract

The agent goal owns the exact validation commands and scenarios. The executor owns focused tests; each batch checkpoint owns its batch tests; one authoritative host/oracle owner runs the broad/full suite once; one owner runs each expensive or live validation once. Other agents may inspect those results but must not duplicate paid/live invocations.

Completion requires a source/evidence-based matrix mapping every agent-goal criterion to its evidence path, command, result, and reviewer disposition, plus a short North Star alignment disposition confirming the desirable end state was advanced and named anti-patterns were avoided. Liveness, process exit, or a passing harness is not a genuine product outcome. Classify stop conditions explicitly: `blocked` (missing authority or external prerequisite), `failed` (reproducible unmet criterion), `undetermined` (insufficient evidence), `retryable` (owned safe retry remains), or `escalate` (risk/authority exceeds the current role). Stop and escalate rather than silently widening scope.

## Phase 6 — Completion

1. End-to-end verification: run the project / full suite; confirm the whole thing executes. Once every segment passes, perform the final integrated oracle review with up to nine independent Sol passes when warranted by integration risk or explicit user direction. Feed the complete North Star into every pass. The final disposition covers both every `agent_goal.md` criterion and North Star alignment/anti-patterns.
2. Commit and sync only under the authorization in `.oracle/agent_goal.md`: stage only reviewed paths, use an explicit remote/refspec, and record the resulting commit. Never infer permission from `northstar.md`, and never infer permission to merge to main, deploy, or promote; those are separate authorized actions.
3. `open` the worktree / project and report phase-by-phase evidence.

## Gotchas

- **Seal codex stdin** with `</dev/null` — otherwise `codex exec` blocks at "Reading additional input from stdin..." with 0% CPU (output file stuck at the banner size). Allow 30 min (`timeout 1800`) for write-heavy/review runs.
- **Delegations need outbound network** — oracle and `[XHARD]` codex runs that delegate must use `--sandbox danger-full-access`; Grok must not pass `--permission-mode plan` when it delegates.
- **Elegance bias is a real instruction** — Sol's revision prompt and every critique brief dispatched to the normal pool must name it (KISS, YAGNI, cut scope); otherwise reasoning models add scope, not subtract it.
- **The pre-settled wave is a placeholder** — leave it empty and do not pretend it ran; record whether it was skipped because the plan was already settled or remained reserved because the plan was still forming. Always run the later settled-plan streamlining wave.
- **Match brief shape to model mode** — normal-pool models receive mechanical, per-batch briefs; architectural judgment stays with the oracle.
- **Liveness ≠ correctness** — a live agent can still answer uselessly; read the response.
- **Review count is intentional** — use the cheap-to-expensive segment sequence (three Luna passes by default, up to five only for disagreement/inconclusive evidence, then at most one Sol oracle pass after Luna convergence) and reserve an integrated final panel of up to nine independent Sol passes for the whole deliverable when warranted. Counts are defaults and explicit user choices control; any `REWORK` blocks escalation, and all passes are bound to frozen artifact/diff identities.
- **Huge runs need cumulative gates** — if estimated implementation effort exceeds two weeks, the oracle chooses and records a risk-based cumulative-review cadence, including major seams, and adjusts it when evidence changes; never wait until the end to detect cross-batch drift.
- **Maximize synchronization, not serialization** — run independent tasks in parallel, then promptly converge code, artifacts, evidence, and reviews on one passed checkpoint; never let dependent work advance from stale or unreviewed state.
- **Model assignment starts with the user** — declare the eligible pools, ask the user to pin each task class or authorize automatic routing, and record the answer in `.oracle/agent_goal.md`. Never switch a pinned model without approval.
- **North Star is direction; agent goal is contract** — `northstar.md` says what durable good looks like and what anti-patterns to avoid; `agent_goal.md` says what this run may do and exactly how it proves completion. Never use the North Star to widen authority.
- **`[XHARD]` means extremely hard** — normal is the default, and many runs should have zero `[XHARD]` tasks. Decompose first; reject any `[XHARD]` tag without concrete evidence that the irreducible task exceeds both normal models.
- **The oracle owns rework triage** — reviewers find issues; the oracle sense-checks them, decides the required revision, emits the supplemental tasklist, and assigns normal versus `[XHARD]` ownership before execution.
- **Checkpoint discipline is the whole game** — skipping the oracle gate to "save a cycle" collapses this into an ungated normal-model run.

## Phase 3 — Revise and sense-check until STABLE

First classify the current plan as **already settled** or **still forming**. A plan is already settled only when it is coherent end to end, its material decisions and dependencies are resolved, no material planning question remains open, and current exploration evidence does not unset it. Record the classification and evidence in `status.md`.

### Pre-settled critique wave — reserved

This stage is intentionally empty for now. Do not infer or invent its prompt, subagents, lenses, artifacts, cadence, or pass criteria. If the plan is already settled—including a supplied or adopted plan that meets the test above—record `skipped: already settled`. If it is still forming, record `reserved: not yet specified` and continue the ordinary explore/revise loop without pretending this placeholder ran.

Once Sol says `STABLE`, run the **settled-plan sense-check wave** before accepting the plan. This is the streamlining and unnecessary-abstraction wave described below. The oracle chooses a useful set of independent normal-pool subagents and critique lenses according to the settled plan's size and risk; there is no fixed critic count or preset lens list. Use the user's declared normal model or authorized automatic routing.

All subagents in the settled-plan wave receive the exact same immutable plan snapshot and digest, plus the complete North Star, frozen agent goal, relevant exploration evidence, prior accepted findings and dispositions, and a narrow mechanical brief. Do not mix plan versions inside one wave. Run independent critics in parallel, then synthesize only after the whole wave returns.

Across the settled-plan wave, challenge whether:

- the outcome can be reached with less work, fewer steps, or fewer handoffs;
- the plan is maximally streamlined and understandable;
- any proposed abstraction, layer, interface, service, configuration surface, or generalization is speculative or unnecessary;
- existing mechanisms can be reused instead of creating parallel ones;
- batches, dependencies, and synchronization points form the simplest safe execution order;
- validation and documentation are sufficient but proportionate rather than ceremonial; and
- every retained element advances an agent-goal criterion and the North Star without reproducing an anti-pattern.

Critics identify and rank concrete simplifications with plan-section or source evidence; they do not widen scope, rewrite the plan, or invent architecture. Save each output as `.oracle/findings/plan-settled-<W>-<lens>.txt` with an invocation receipt. After every subagent in the wave returns, the oracle writes `.oracle/findings/plan-settled-<W>-synthesis.md`, deduplicating findings and recording `accept`, `reject`, or `investigate` with rationale. Feed accepted findings to Sol for a full-plan revision.

If a settled-plan finding materially reopens the plan, classify it as still forming and return to the ordinary explore/revise loop; the pre-settled slot remains unexecuted until its contract is defined. Once Sol says `STABLE` again, always run a fresh settled-plan wave on the entire revised plan, not merely the edited sections. The plan is finally settled only when Sol says `STABLE` and the latest complete settled-plan wave yields no accepted material simplification or unresolved investigation. If critics repeat a settled objection without new evidence, cite the prior disposition rather than looping indefinitely. Then continue to the independent pre-execution contract review in Phase 4.

```bash
# Megado

Plan → explore → revise → execute → oracle-gate → sync, all in a worktree, never on main.

- **Planner** — GPT-5.6 Sol (codex exec, high reasoning): tasklist, revision, batch design.
- **Plan sense-checkers** — independent DeepSeek V4 Flash or GPT-5.6 Luna subagents: challenge simplicity, scope, abstractions, sequencing, and verification before the plan freezes.
- **Explorer / normal Executor** — DeepSeek V4 Flash or GPT-5.6 Luna, selected by the user's run declaration.
- **Oracle / sense checker** — GPT-5.6 Sol or Grok 4.6 (grok CLI): gates every batch, finalizes normal versus `[XHARD]` classification, applies the user's model declaration, and decides what rework is actually required.
- **`[XHARD]` Executor** — GPT-5.6 Sol or Grok 4.6, reserved for exceptionally hard tasks and selected by the user's run declaration.

One orchestrator (the host) drives all phases, holds the `.oracle/` artifacts, and writes every brief. Automatic routing may move between eligible models; a user-pinned model requires user approval before any switch.

## North Star, agent goal, and source custody

Before planning, create or adopt `.oracle/northstar.md`, then freeze `.oracle/agent_goal.md`. The agent goal must link to the North Star with `[North Star](./northstar.md)`.

**`northstar.md` is the durable direction.** Keep it succinct—normally one page or less. It explains:

- the desirable end state in plain language;
- the enduring qualities, principles, or invariants the work should preserve;
- the important anti-patterns, failure modes, and hollow versions of success to avoid;
- what aligned progress should feel or look like across multiple batches or runs.

The North Star is not a task list, acceptance checklist, source manifest, validation plan, or authorization document. It should not contain run-local implementation detail. If a durable project North Star already exists, snapshot or copy it into `.oracle/northstar.md` and record its source path and digest in custody rather than casually rewriting it.

**`agent_goal.md` is the frozen operational contract for this run.** It records:

- the concrete objective and end-state contribution for this agent;
- the North Star link plus one sentence explaining how this run advances it;
- authoritative inputs and immutable source ref;
- in-scope work, non-goals, settled decisions, and open boundaries;
- authorization boundaries, including mutation, sync, promotion, and deployment;
- the user-declared model policy;
- exact done and stop criteria;
- final validation commands and scenarios;
- sync/promotion policy.

The North Star provides alignment, never authority: it cannot widen the agent goal's scope, permissions, or done criteria. If the documents conflict, stop and reconcile the conflict with the user rather than choosing one silently. The plan may evolve within the agent goal; it must not silently change either document. Changing the North Star requires explicit user agreement and a fresh review of `agent_goal.md` against it.

**North Star propagation is mandatory.** Every model-facing unit of work—planning or revision prompt, settled-plan sense-check brief, exploration brief, task or rework item, executor brief, validation brief, routine check-in, cumulative big-batch review, re-review, and final overall review—must receive the complete contents of `.oracle/northstar.md`, not merely a path or link. Every task record names the relevant North Star principle or anti-pattern, or explicitly says that none is task-specific. Every execution brief instructs the model to advance the stated end state and avoid the named anti-patterns without widening `agent_goal.md`; every review verdict includes an explicit North Star alignment disposition. Record the North Star digest in every invocation receipt so the run can prove which version each model saw. If the North Star changes, do not let pending work silently inherit it: re-review `agent_goal.md`, regenerate affected briefs, and freshly review affected open tasks.

Keep that baseline with the run and identify the base SHA in every receipt.

## Execution model routing

The skill fixes the **eligible pools**, not the exact model:

- **Normal tasks:** DeepSeek V4 Flash or GPT-5.6 Luna.
- **`[XHARD]` tasks:** GPT-5.6 Sol or Grok 4.6.

The user's declaration controls assignment. If the user selected a model for a class, use it for that class. If the user selected automatic routing, the run's judgment owner—the oracle in Megado, the integrator in Microdo—first classifies the task, then selects one eligible model based on task fit, context continuity, tool needs, and current model availability or health. Record the classification, selected model, and rationale (`user-selected` or the automatic-routing reason) in the tasklist or rework tasklist and invocation receipt. Never treat a previous task's model as a default unless the user's declaration fixed it for the run.

## `[XHARD]` threshold

**Normal is the default. `[XHARD]` is an exceptional classification for extremely hard work; many runs should have no `[XHARD]` tasks at all.** First decompose the work into clear, bounded tasks. Classify only the irreducible remainder as `[XHARD]`, and only when the judgment owner can show that:

- it requires sustained, subtle reasoning or novel judgment across tightly coupled concerns;
- a plausible mistake could survive ordinary local validation and cause non-local or hard-to-detect harm; and
- neither DeepSeek V4 Flash nor GPT-5.6 Luna can be expected to execute it reliably from a precise mechanical brief.

Size, file count, importance, unfamiliarity, cross-cutting scope, write volume, time pressure, or one failed normal-model attempt do **not** make a task `[XHARD]` by themselves. Diagnose brief quality, environment, tools, and decomposition before escalating. Prefer keeping tractable subparts normal and assigning only the genuinely irreducible judgment kernel to `[XHARD]`. When uncertain, classify the task as normal.

Every `[XHARD]` tag requires a concrete written rationale stating why decomposition is insufficient and why the normal pool is not reliable for this specific task. A label without that evidence must be rejected by the oracle/integrator.

## Delegation mandate — verbatim in every oracle check-in brief and `[XHARD]` task brief

> DELEGATION MANDATE — You are a manager and validator of the normal execution pool, NOT a worker. Delegate as much as possible to the task's selected normal model: DeepSeek V4 Flash or GPT-5.6 Luna. Flash invocation: `omp -p @<brief>.md --model deepseek-v4-flash --cwd <worktree> --no-session --auto-approve --max-time=1800`; Luna invocation: `launch_hermes_agent.py --model="codex:gpt-5.6-luna" --query-file=<brief> --project-dir=<worktree>` (research-only briefs use read/search tools). Dispatch research, execution, and critique briefs to the selected model — critique passes optimize for elegance: KISS, YAGNI, cut scope that isn't pulling its weight; flag overengineering, not just bugs. Your job is to direct, then validate: read delegated output against the acceptance criteria; do work yourself only when delegation is impossible — the selected normal model already failed at it, or the piece is too small / too tightly coupled to your own reasoning to hand off. If you catch yourself implementing or researching directly, stop and ask whether a normal-pool brief would cover it. It almost always would.

## Oracle review count

Here, a **review pass** means one independent reviewer produces one verdict against the full acceptance criteria. The oracle's own synthesis and final `PASS`/issues judgment do not count as another pass.

The reserved pre-settled critique slot is not currently a review. Settled-plan sense-check waves are targeted critiques rather than full acceptance-criteria verdicts, so they do not count as Oracle review passes. They may not replace the fresh independent pre-execution contract review.

Use a cheap-to-expensive escalation for each segment (routine batch, cumulative boundary, or rework packet):

- **Segment review:** default to **three independent GPT-5.6 Luna** passes against the same frozen packet. They are separate verdicts, not a single panel or a synthesis of one another.
- **Expand only on evidence:** commission up to **five Luna** passes only when the initial passes disagree, a pass is unusable/inconclusive, or the evidence conflicts. Record the trigger and resolution. Do not spend a higher-cost review to rescue a known-broken candidate.
- **Rework gate:** any `REWORK` verdict blocks escalation and downstream work. After correction, create a fresh review packet bound to the new artifact identities and restart the segment review sequence; a prior reviewer process or verdict does not count for the corrected candidate.
- **Segment Sol oracle:** after Luna reaches convergence on `PASS`, commission at most **one GPT-5.6 Sol** oracle review for that segment, only when the segment's risk or the user's instructions warrant it. Sol reviews the same frozen identities and must not be used to bless an unresolved `REWORK`.
- **Final integrated panel:** once all segments pass, commission up to **nine independent GPT-5.6 Sol** passes for the whole deliverable when warranted by integration risk or explicit user direction. The panel synthesis is separate and does not add another pass.

These counts are defaults, not a license to widen scope: explicit user model or count choices control, and the existing model-routing and fallback rules still apply. Every pass must record the immutable source/checkpoint, brief, manifest, and diff identities it reviewed. The oracle records why it stopped at the selected count and why any escalation was proportionate.

## Huge-run periodic cumulative reviews

During planning, record the planner's best-effort estimate of total end-to-end implementation effort in `plan.md` and the current huge-run state in `status.md`. If it is **greater than two weeks**, mark the run as a **huge run** and activate periodic cumulative big-batch reviews. This is a review policy inside Megado; it does not by itself change the user's requested execution mechanism. If a run initially estimated at two weeks or less later grows beyond the threshold, activate the policy before executing the next batch and record the revised estimate and reason in both files. Do not mutate the frozen `agent_goal.md` merely to store sizing metadata.
```

**3. Rework triage — oracle as sense checker.** A reviewer reports findings; the oracle decides which findings require action and what revision is needed. Before dispatching any fix, the oracle writes `.oracle/rework/batch-<N>-attempt-<M>.md`, a supplemental tasklist shaped like the main tasklist. It does not silently edit the frozen `.oracle/tasklist.md`.

For every accepted finding, the rework tasklist records:

- the finding and supporting evidence;
- the affected agent-goal criterion and relevant North Star principle or anti-pattern, when applicable;
- the required outcome and affected scope;
- dependencies and execution order;
- the oracle's **normal** or **`[XHARD]`** classification; `[XHARD]` requires the full exceptional-threshold rationale;
- the selected model: DeepSeek V4 Flash or GPT-5.6 Luna for normal work; GPT-5.6 Sol or Grok 4.6 for `[XHARD]` work;
- acceptance criteria and exact validation.

The oracle—not the reviewer or executor—owns this triage and complexity decision. It may delegate investigation, but it must presume normal work, attempt sensible decomposition, and reserve `[XHARD]` for an irreducible revision that satisfies every part of the exceptional threshold. A large, important, unfamiliar, cross-cutting, or write-heavy fix is still normal unless the recorded evidence proves otherwise. If a finding would change the frozen agent goal, the North Star, or materially revise the stable plan, route it through the existing user-authorization and full-review process instead of disguising it as ordinary rework.

**4. Rework execution and re-review.** Generate executor briefs from the supplemental tasklist, embedding the complete North Star in every brief and preserving each rework item's alignment/anti-pattern instruction. Execute the normal and `[XHARD]` items with their assigned models, commit the revised batch, create a fresh packet bound to the revised artifact identities, and restart the segment review sequence under the Oracle review count policy. Repeat the triage → tasklist → execution → fresh-review loop until the oracle passes. Record each finding, tasklist, revision, result digest, actual model/provider, command, cwd, base/head SHAs, North Star digest, PID/timestamps/exit, and evidence paths. An implementer or revision agent never reviews its own work. **Do not start batch N+1 until batch N passes.**

**5. Huge-run cumulative gate.** When the current passed batch reaches a predeclared huge-run boundary, perform the periodic cumulative big-batch review before starting the next batch. Treat the cumulative boundary as its own segment: use the complete cumulative scope and artifacts required by Huge-run periodic cumulative reviews, start with three independent Luna passes, expand only on disagreement or inconclusive/conflicting evidence, and after Luna convergence may commission at most one Sol oracle pass when warranted. Any `REWORK` requires correction, a fresh packet, and a restarted review sequence; a routine batch pass cannot substitute for this gate, which must reach `PASS`.

## Validation and completion contract

The agent goal owns the exact validation commands and scenarios. The executor owns focused tests; each batch checkpoint owns its batch tests; one authoritative host/oracle owner runs the broad/full suite once; one owner runs each expensive or live validation once. Other agents may inspect those results but must not duplicate paid/live invocations.

Completion requires a source/evidence-based matrix mapping every agent-goal criterion to its evidence path, command, result, and reviewer disposition, plus a short North Star alignment disposition confirming the desirable end state was advanced and named anti-patterns were avoided. Liveness, process exit, or a passing harness is not a genuine product outcome. Classify stop conditions explicitly: `blocked` (missing authority or external prerequisite), `failed` (reproducible unmet criterion), `undetermined` (insufficient evidence), `retryable` (owned safe retry remains), or `escalate` (risk/authority exceeds the current role). Stop and escalate rather than silently widening scope.

## Phase 6 — Completion

1. End-to-end verification: run the project / full suite; confirm the whole thing executes. Once every segment passes, perform the final integrated oracle review with up to nine independent Sol passes when warranted by integration risk or explicit user direction. Feed the complete North Star into every pass. The final disposition covers both every `agent_goal.md` criterion and North Star alignment/anti-patterns.
2. Commit and sync only under the authorization in `.oracle/agent_goal.md`: stage only reviewed paths, use an explicit remote/refspec, and record the resulting commit. Never infer permission from `northstar.md`, and never infer permission to merge to main, deploy, or promote; those are separate authorized actions.
3. `open` the worktree / project and report phase-by-phase evidence.

## Gotchas

- **Seal codex stdin** with `</dev/null` — otherwise `codex exec` blocks at "Reading additional input from stdin..." with 0% CPU (output file stuck at the banner size). Allow 30 min (`timeout 1800`) for write-heavy/review runs.
- **Delegations need outbound network** — oracle and `[XHARD]` codex runs that delegate must use `--sandbox danger-full-access`; Grok must not pass `--permission-mode plan` when it delegates.
- **Elegance bias is a real instruction** — Sol's revision prompt and every critique brief dispatched to the normal pool must name it (KISS, YAGNI, cut scope); otherwise reasoning models add scope, not subtract it.
- **The pre-settled wave is a placeholder** — leave it empty and do not pretend it ran; record whether it was skipped because the plan was already settled or remained reserved because the plan was still forming. Always run the later settled-plan streamlining wave.
- **Match brief shape to model mode** — normal-pool models receive mechanical, per-batch briefs; architectural judgment stays with the oracle.
- **Liveness ≠ correctness** — a live agent can still answer uselessly; read the response.
- **Review count is intentional** — use the cheap-to-expensive segment sequence (three Luna passes by default, up to five only for disagreement/inconclusive evidence, then at most one Sol oracle pass after Luna convergence) and reserve an integrated final panel of up to nine independent Sol passes for the whole deliverable when warranted. Counts are defaults and explicit user choices control; any `REWORK` blocks escalation, and all passes are bound to frozen artifact/diff identities.
- **Huge runs need cumulative gates** — if estimated implementation effort exceeds two weeks, the oracle chooses and records a risk-based cumulative-review cadence, including major seams, and adjusts it when evidence changes; never wait until the end to detect cross-batch drift.
- **Maximize synchronization, not serialization** — run independent tasks in parallel, then promptly converge code, artifacts, evidence, and reviews on one passed checkpoint; never let dependent work advance from stale or unreviewed state.
- **Model assignment starts with the user** — declare the eligible pools, ask the user to pin each task class or authorize automatic routing, and record the answer in `.oracle/agent_goal.md`. Never switch a pinned model without approval.
- **North Star is direction; agent goal is contract** — `northstar.md` says what durable good looks like and what anti-patterns to avoid; `agent_goal.md` says what this run may do and exactly how it proves completion. Never use the North Star to widen authority.
- **`[XHARD]` means extremely hard** — normal is the default, and many runs should have zero `[XHARD]` tasks. Decompose first; reject any `[XHARD]` tag without concrete evidence that the irreducible task exceeds both normal models.
- **The oracle owns rework triage** — reviewers find issues; the oracle sense-checks them, decides the required revision, emits the supplemental tasklist, and assigns normal versus `[XHARD]` ownership before execution.
- **Checkpoint discipline is the whole game** — skipping the oracle gate to "save a cycle" collapses this into an ungated normal-model run.

# North Star — one canonical Astrid pack

Astrid has one understandable pack concept. Every bundled product extension is
owned by one strict `pack.yaml`; a pack may contribute capabilities, SQLite
schema, agent documentation, or any combination. `timeline`, `shots`,
`references`, and `runaway` are ordinary bundled packs rather than a second
schema-pack species.

Opening a pack directory should reveal one authoritative declaration of its
identity, resources, custom capabilities, database ownership, migrations,
events, commands, CLI surface, and agent guidance. Runtime systems consume
typed projections of that declaration instead of independently rediscovering
or reinterpreting the pack. Every existing bundled customization is either
owned by a canonical pack or explicitly classified as irreducible kernel
behavior; nothing remains unclassified.

## Enduring principles

- One pack identity, manifest grammar, parser/validator, normalized definition,
  and bundled catalog.
- SQLite remains the per-project authority. Migration SQL owns columns,
  constraints, indexes, and transformations; YAML does not duplicate DDL.
- Reuse the strong machinery already present: typed registries, migration
  ordering/checksums/drift/transactions, `DatabaseWriter`, `UnitOfWork`,
  repositories, SDK behavior, and conformance tests.
- Bundled trusted packs may contribute database schema; external packs remain
  capability-only during beta.
- Every pack-relative resource is confined, discoverable, and present in the
  built wheel.
- Every user/agent-facing bundled pack ships structured agent documentation;
  the `_core` skill exposes a generated canonical pack census and routes agents
  to the owning pack documentation.
- With no users to migrate, cut directly to the final form and delete alternate
  authorities instead of maintaining shims.
- Keep beta scope proportionate: unify today's bundled system without
  prebuilding a marketplace or variable project-composition lifecycle.

## Anti-patterns

- Hiding the old schema-pack subsystem inside `pack.yaml` while retaining its
  parser, identity, discovery, or hard-coded standard list.
- Replacing useful typed registries with a giant universal service locator.
- Duplicating SQLite DDL or mutable runtime facts in YAML or skill prose.
- Per-project pack locks, enable/disable/purge state machines, dynamic database
  plugins, or migration ceremony without an observed beta need.
- Allowing external packs to execute SQL.
- Making the irreducible kernel dynamically unloadable for conceptual symmetry.
- Compatibility shims, dual reads, schema-less manifests, or legacy fallbacks.
- Declaring success while any bundled customization, documentation surface,
  operational consumer, or packaged resource bypasses canonical ownership.

## Accepted material changes

1. **Composition algorithm, not named set.** Standard composition selects every
   trusted bundled catalog entry with `database` and dependency-orders that

   permitted declaration/projection API. The catalog never constructs services;
   typed registries/static factories retain runtime construction ownership.
3. **Freeze a field-level v2 contract before parallel implementation.** Record
   required/optional fields, normalized types, contribution constraints,
   resource grammar, documentation routing, provenance/trust semantics, and
   invalid cases in schema plus golden fixtures.

   reachable through a declared contribution or used by pack runtime code must
   be declared through one typed resource or explicit supplemental resource.
   Closure is recursive, owner-relative, realpath-confined, source/wheel equal,
   and rejects undeclared required assets.

   let the WP0 snapshot become stale runtime truth.

   references, and runaway across every applicable migration/repository/event/
   command/CLI/SDK/conformance surface, with explicit N/A reasons where a pack
   intentionally has no surface.

   imports, parser entry points, and fixed authorities. Prefer loader/catalog,
   coverage, AST/import, and clean-wheel semantic checks over broad textual
   regex scans that would flag historical or unrelated material.
