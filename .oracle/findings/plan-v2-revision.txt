# North Star — one canonical Astrid pack

Astrid has one understandable pack concept. Every bundled product extension is
owned by one strict `pack.yaml`; a pack may contribute capabilities, SQLite
schema, agent documentation, or any combination. `timeline`, `shots`,
`references`, and `runaway` are ordinary bundled packs rather than a second
schema-pack species.

Opening a pack directory should reveal one authoritative declaration of its
identity, resources, custom capabilities, database ownership, migrations,
events, commands, CLI surface, and agent guidance. Runtime systems consume
typed projections of that declaration instead of independently rediscovering
or reinterpreting the pack. Every existing bundled customization is either
owned by a canonical pack or explicitly classified as irreducible kernel
behavior; nothing remains unclassified.

## Enduring principles

- One pack identity, manifest grammar, parser/validator, normalized definition,
  and bundled catalog.
- SQLite remains the per-project authority. Migration SQL owns columns,
  constraints, indexes, and transformations; YAML does not duplicate DDL.
- Reuse the strong machinery already present: typed registries, migration
  ordering/checksums/drift/transactions, `DatabaseWriter`, `UnitOfWork`,
  repositories, SDK behavior, and conformance tests.
- Bundled trusted packs may contribute database schema; external packs remain
  capability-only during beta.
- Every pack-relative resource is confined, discoverable, and present in the
  built wheel.
- Every user/agent-facing bundled pack ships structured agent documentation;
  the `_core` skill exposes a generated canonical pack census and routes agents
  to the owning pack documentation.
- With no users to migrate, cut directly to the final form and delete alternate
  authorities instead of maintaining shims.
- Keep beta scope proportionate: unify today's bundled system without
  prebuilding a marketplace or variable project-composition lifecycle.

## Anti-patterns

- Hiding the old schema-pack subsystem inside `pack.yaml` while retaining its
  parser, identity, discovery, or hard-coded standard list.
- Replacing useful typed registries with a giant universal service locator.
- Duplicating SQLite DDL or mutable runtime facts in YAML or skill prose.
- Per-project pack locks, enable/disable/purge state machines, dynamic database
  plugins, or migration ceremony without an observed beta need.
- Allowing external packs to execute SQL.
- Making the irreducible kernel dynamically unloadable for conceptual symmetry.
- Compatibility shims, dual reads, schema-less manifests, or legacy fallbacks.
- Declaring success while any bundled customization, documentation surface,
  operational consumer, or packaged resource bypasses canonical ownership.

## Final architecture

### Canonical definition and catalog

- Evolve `PackDefinition` in place into the single complete, deeply immutable v2 object.
- Load only `pack.yaml` with required `schema_version: 2`.
- Reject `pack.yml`, `pack.json`, schema-less YAML, unknown legacy shapes, and `schema-pack.yaml`.
- Parse and validate once. Static validation, installation, inspection, agent indexing, registries, and packaging consume the same normalized definition.
- Include normalized identity, resources, capabilities, database contribution, vocabularies, repositories, conformance declarations, static CLI/bridge ownership, and agent-documentation routes.
- Attach source kind, pack root, installed revision, and bundled trust as loader/catalog provenance. They are not self-declared manifest authority.
- Keep install metadata only as transport/revision state; it must not reconstruct canonical pack identity.
- Preserve automatic local-pack creation, but emit strict capability-only v2 and hard-fail existing legacy local manifests.

### Typed projections

- The catalog exposes narrow projections for executor, orchestrator, element, rendering, generation, database, CLI ownership, skills, inspection, and resource closure.
- Existing typed registries retain their specialized behavior and validation.
- Discovery order and provenance are preserved through projections; no API strips catalog entries to identity-only objects before admission checks.
- Static application, repository, service, CLI, and bridge factories remain where already useful. The catalog does not instantiate arbitrary services.

### Database contribution

- Core migrations remain explicit irreducible kernel behavior.
- A bundled pack may declare an optional database contribution containing ownership and typed migration/resource metadata. SQL remains authoritative for columns, constraints, indexes, and transformations.
- Standard composition is core plus all trusted bundled database contributions from the catalog: `references`, `runaway`, `shots`, and `timeline` in deterministic dependency order.
- Reuse the existing collision registry and migration runner after relocating them out of schema-pack identity code.
- `RegisteredMigration` gains its owner-relative resolved resource handle and provenance/revision information.
- Enforce dependency existence, cycles, and declared minimum versions before registration.
- Preserve exact SQL bytes, migration identity, checksums, drift detection, probe behavior, and per-migration `BEGIN IMMEDIATE` transactions.
- External packs with `database` fail at catalog admission across local, extra-root, environment, Git-installed, and active installed-revision paths, before SQL resolution or registration.

### Documentation and census

- Every retained bundled product pack declares a structured `skill/SKILL.md`.
- Add direct pack guidance for the five documented gaps and repair `media` frontmatter.
- `_core` remains kernel-owned and non-unloadable. It links a generated, packaged canonical census containing stable pack identity, capability categories, database ownership, and routes to owning documentation.
- The census contains no duplicated DDL or mutable database status.
- Use one deterministic generator with check mode; remove independent skill and agent-index manifest parsing.

### Coverage ledger

Create a reviewed, non-runtime coverage ledger with:

- `surface_id`
- `kind`
- `owner` as `pack:<id>` or `kernel:<subsystem>`
- `evidence_paths`
- `projection_consumers`

Kinds cover capability components, rendering protocols, database migrations/table ownership, vocabularies, repositories, conformance, CLI/SDK/bridge surfaces, resources, documentation, and operational consumers.

The checker must reject missing, stale, duplicate, or conflicting ownership. Consumers are recorded as consumers, never treated as owners. `builtin` and its aliases are recorded as deleted compatibility residue, not converted into artificial ownership.

## Explicit anti-pattern rejections

1. **No concealed schema-pack subsystem.** Its manifests, parser, identities, fixed lists, imports, and tests are deleted; only relocated generic migration mechanics survive.
2. **No universal service locator.** The catalog supplies immutable ownership data and narrow projections; existing typed registries and static factories remain.
3. **No duplicated SQLite authority.** YAML declares ownership and migration resources only; SQL owns DDL and `schema_migrations` owns applied state. Skills and census prose contain neither DDL nor mutable status.
4. **No composition lifecycle machinery.** No project pack locks, enable/disable/purge state machines, dynamic database plugins, down migrations, or unused migration ceremony.
5. **No external SQL.** Every non-bundled database declaration fails before resource resolution, registry registration, or database access.
6. **No unloadable kernel fiction.** Core migrations and primitives remain code-owned; `_core` remains a permanent kernel documentation/router surface.
7. **No compatibility layer.** No dual reads, aliases, schema-less manifests, legacy filenames, fallback parsers, re-exports, or v1-to-v2 shims.
8. **No partial-success declaration.** Final gates cover all bundled custom surfaces, documentation, operational consumers, generated census data, and wheel resources; any bypass or unclassified surface fails the run.

## Scope cuts and simplicity controls

- Delete `builtin` rather than inventing a purpose for an empty pack.
- Delete deprecated aliases rather than carrying beta compatibility residue.
- Do not build a marketplace, dependency solver, activation framework, signing system, database plugin interface, or general service factory.
- Do not redesign existing repositories, `DatabaseWriter`, `UnitOfWork`, SDK behavior, or migration transactions.
- Do not make the coverage ledger a runtime registry.
- Do not introduce a custom packaging backend when ordinary package-data rules plus installed-wheel closure tests suffice.
- Do not treat unrelated training manifests as pack manifests.
- Do not duplicate pack census logic across `_core`, skills, inspect, and doctor.
- Do not widen the goal to global models, LoRAs, taxonomies, or kernel primitives unless the zero-unclassified audit proves an existing pack-owned customization requires classification.

## Explicit anti-pattern rejections

1. **No concealed schema-pack subsystem.** Its manifests, parser, identities, fixed lists, imports, and tests are deleted; only relocated generic migration mechanics survive.
2. **No universal service locator.** The catalog supplies immutable ownership data and narrow projections; existing typed registries and static factories remain.
3. **No duplicated SQLite authority.** YAML declares ownership and migration resources only; SQL owns DDL and `schema_migrations` owns applied state. Skills and census prose contain neither DDL nor mutable status.
4. **No composition lifecycle machinery.** No project pack locks, enable/disable/purge state machines, dynamic database plugins, down migrations, or unused migration ceremony.
5. **No external SQL.** Every non-bundled database declaration fails before resource resolution, registry registration, or database access.
6. **No unloadable kernel fiction.** Core migrations and primitives remain code-owned; `_core` remains a permanent kernel documentation/router surface.
7. **No compatibility layer.** No dual reads, aliases, schema-less manifests, legacy filenames, fallback parsers, re-exports, or v1-to-v2 shims.
8. **No partial-success declaration.** Final gates cover all bundled custom surfaces, documentation, operational consumers, generated census data, and wheel resources; any bypass or unclassified surface fails the run.

## Scope cuts and simplicity controls

- Delete `builtin` rather than inventing a purpose for an empty pack.
- Delete deprecated aliases rather than carrying beta compatibility residue.
- Do not build a marketplace, dependency solver, activation framework, signing system, database plugin interface, or general service factory.
- Do not redesign existing repositories, `DatabaseWriter`, `UnitOfWork`, SDK behavior, or migration transactions.
- Do not make the coverage ledger a runtime registry.
- Do not introduce a custom packaging backend when ordinary package-data rules plus installed-wheel closure tests suffice.
- Do not treat unrelated training manifests as pack manifests.
- Do not duplicate pack census logic across `_core`, skills, inspect, and doctor.
- Do not widen the goal to global models, LoRAs, taxonomies, or kernel primitives unless the zero-unclassified audit proves an existing pack-owned customization requires classification.
